# Проверки функций SDK — проектные требования качества

Ниже инженерные меры набора. Конкретные API и разрешения — в документе площадки, а не в универсальных предположениях.

## Lifecycle и загрузка
Инициализировать один раз; ограничить ожидание и показать понятный retry/guest fallback, если разрешён. SDK not available в локальном режиме не равен production ready. ready отправлять после появления первого интерактивного экрана с нужными ассетами; не при создании canvas. Gameplay start/stop должны соответствовать определению площадки.

## Реклама
Rewarded — добровольная кнопка с ясным бонусом. На один запрос создать request ID и lock от повторного нажатия. Начислять лишь по документированному подтверждению завершения. Закрытие, resolve без подтверждения, no-fill и error не являются наградой. Дубли callbacks не должны удваивать выплату.
Реклама между уровнями не прерывает drag/нажатие/бой; решение показа внутри платформы не заменяет продуманное placement. Не ставить setInterval для неожиданного fullscreen.
Пауза/звук/input сохраняются до корректного завершения; при возвращении focus не перебивает активную рекламу. При потерянном callback и timeout не возобновлять бой за видимым объявлением: иметь безопасный recovery и следовать lifecycle хоста.
В no-ad режиме игрок продолжает основной цикл. Тестовая награда и mock-ad явно development only, отсутствуют в release.

## Покупки
До реализации подтвердить доступ кабинета и договор. Начальный MVP рекомендуется без IAP, если механика живёт на рекламе.
Каталог, цена, валюта и локаль — от площадки. Хранить product type: consumable / durable, количество и идентификатор транзакции. Поддерживать cancel, error, pending, duplicate, reload после оплаты, недоставленный товар и восстановление.
Логический порядок: получить/проверить покупку → атомарно зафиксировать entitlement и transaction ID в доверенном/надёжном состоянии → выполнить платформенный consume/ack там, где требуется → повторный запуск восстанавливает недоделанный шаг без повторной награды. Конкретная транзакционная схема зависит от SDK; не придумывать серверный контракт.
Не принимать клиентский флаг paid=true за проверку реального платежа на своём backend. Не хранить секреты в JS/C#, PlayerPrefs, HTML и конфиге сборки. Создание сервера, обработка персональных данных и платный SaaS — новый scope.

## Сохранения и авторизация
Проверить гостя, отказ во входе, позднюю cloud-загрузку, медленный интернет, повторное открытие, logout/account switch, недоступное storage и повреждённый JSON. Не блокировать основной цикл обязательным внешним логином, если хост этого не разрешает.
Локальное сохранение может отсутствовать/быть очищено; try/catch обязателен для браузерного хранилища. Нельзя заменять неполученный cloud пустым save. Согласовать offline idle-cap и защиту от перевода часов; это изменение экономики, не автоматическая SDK-правка.

## Лидерборды
Сначала решить, нужен ли вообще общий рейтинг. Для MVP личный рекорд достаточен для многих игр. Глобальная таблица нужна только с реальными пользователями/сервером площадки/одобренным SaaS.
Записать metric, единицы, ASC/DESC, период, tie-break, допустимые пределы, идентификатор, доступ гостя и частоту запросов. Отправлять по результату уровня/забега, не покадрово. Лидеры с фиктивными именами — не глобальный рейтинг.
Результат, вычисленный исключительно клиентом, уязвим для читов. Не строить денежные призы/ценные турниры на такой архитектуре. Native leaderboard и backend leaderboard — разные реализации, проверять отдельно. Без подтверждённой поддержки скрыть кнопку, не падать.

## Аналитика
До выбора сервиса описать лишь события: first_interaction, tutorial_complete, level_start/end/fail, upgrade, save_error, ad_offer/request/result и purchase_result при IAP. Не логировать персональные данные или платёжные токены. Платформенная аналитика приоритетна; внешний SDK только после проверки правил и разрешения владельца.
