# Порядок работ и разрешения

## 0. Инвентаризация без записи
Прочитать инструкции; определить фактический корень игры; посмотреть Git status/diff без reset. Не читать содержимое .env, ключей и сертификатов. Обнаружить конфиги, но не публиковать секреты.
Результат: движок/версия, команда сборки из проекта, существующие SDK, сцены/экраны, сохранение, звуковой менеджер, точки lifecycle, устройства, технические проблемы. Утилита inspect_project — только первичный указатель, не полноценный аудит.

## 1. MVP
Подтверждаются запуск, понятный первый шаг, один законченный цикл, проигрыш/победа/повтор, сохранение и повторная загрузка, mouse/touch, маленький экран, mute, отсутствие критических ошибок. Дополнительные функции не добавляются ради чек-листа: например, конечная головоломка может не иметь магазина и idle-прогресса.
Критерии и минимальный контент согласовать. Новая игра: сначала несколько полностью проходимых уровней, не сотни заготовок. Не менять экономику под рекламу без отдельного решения.

## 2. Выбор площадки
Вопрос о площадке задаётся после подтверждения MVP, а не после автоматической интеграции SDK. Если цель уже известна, подтвердить её в профиле. Не задавать всё повторно.
Развести платформу показа, тип приложения, SDK-провайдера, хостинг и сторону договора. Один выбор не определяет остальные.

## 3. Две независимые двери
Техническая: подтверждены требования и доступные API. Коммерческая: владелец подтвердил возможность договора/получения денег и отсутствие конфликтов прав. Технический эксперимент допустим при незакрытом коммерческом вопросе только с явно принятым владельцем риском; платный backend и публикация остаются запрещены.

## 4. План и разрешения
В INTEGRATION_PLAN указать create/modify/read для каждого файла, размер/смысл правки, команды и создаваемые каталоги, зависимости, ручные действия, тесты и rollback.
В APPROVAL_LOG — ссылка на сообщение/дата, scope и что точно не разрешено. Разрешение на docs ≠ разрешение на код. Разрешение на установку SDK ≠ разрешение на обновление Phaser.
Если текущая архитектура не позволяет локальное подключение — объяснить конкретное препятствие и предложить минимальную альтернативу; не начинать рефакторинг молча.

## 5. Маленькие патчи
Сначала обвязка lifecycle и отсутствие ошибок, затем реклама, затем сохранения, затем опциональные leaderboard/IAP. Каждый шаг подтверждается тестами, исходная платформа не ломается. Промежуточные mock-события только явно в development, в production такой режим запрещён.

## 6. Подготовка подачи
Проверить docs выбранной платформы и кабинет. Проверить ZIP и запуск по HTTP/в настоящем iframe. Отчёт не объявлять PASS, если это только тест на localhost.
Нет ID/доступа/кабинетного теста — назвать конкретный блокер, оставить работающий локальный режим. Не выдумывать успешный платёж.
