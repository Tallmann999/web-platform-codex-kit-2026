# Web Platform Release Kit

Набор правил, документов и утилит для подготовки web-игр к публикации на разных игровых платформах.

Проект предназначен для работы вместе с **Codex** и помогает безопасно готовить одну и ту же игру под несколько площадок без хаотичного изменения архитектуры проекта.

Основная идея:

**Сначала игра → потом MVP → затем выбор платформы → только после этого SDK и отдельная сборка.**

---

## Для чего нужен этот репозиторий

`Web Platform Release Kit` помогает организовать подготовку HTML5 / Phaser / Unity WebGL игр к публикации на web-площадках.

Kit нужен, чтобы Codex:

- сначала изучал существующий проект;
- проверял готовность MVP;
- не подключал SDK раньше времени;
- спрашивал, под какую платформу готовится билд;
- проверял актуальные требования выбранной площадки;
- предлагал минимальные изменения;
- не переписывал глобальные системы без разрешения;
- создавал отдельную конфигурацию для каждой платформы;
- документировал все изменения;
- отдельно проверял рекламу, сохранения, покупки и лидерборды;
- не смешивал SDK разных площадок внутри основной игровой логики.

---

## Поддерживаемые направления

В комплекте предусмотрены документы и правила для следующих web-платформ:

1. **Яндекс Игры**
2. **CrazyGames**
3. **Poki**
4. **GameDistribution**
5. **Playgama**
6. **VK**
7. **Одноклассники / VK Mini Apps**

Перед каждой интеграцией требования платформы должны перепроверяться, потому что SDK, правила монетизации и условия публикации со временем меняются.

## Главный принцип работы

Codex должен соблюдать следующий порядок:

```text
Чтение проекта
    ↓
Проверка MVP
    ↓
Определение готовности игры
    ↓
Выбор платформы
    ↓
Проверка актуальной документации платформы
    ↓
План интеграции
    ↓
Согласование изменений
    ↓
Подключение SDK
    ↓
Отдельная сборка
    ↓
Тестирование
    ↓
Release Checklist
```

SDK конкретной площадки не должен становиться частью core gameplay.

Игровая логика должна оставаться максимально независимой от:

- рекламы;
- авторизации;
- лидербордов;
- облачных сохранений;
- внутриигровых покупок;
- API конкретного портала.

## Установка Skill в игровой проект

Скопируйте каталог:

```text
.agents/skills/web-platform-release/
```

в **корень репозитория игры**.

Не помещайте его внутрь:

```text
Assets/
src/
Build/
dist/
public/
```

Рекомендуемая структура:

```text
MyGame/
│
├── .agents/
│   └── skills/
│       └── web-platform-release/
│
├── docs/
├── src/
├── assets/
├── build/
├── AGENTS.md
└── README.md
```

---

## AGENTS.md

В комплекте находится файл:

```text
AGENTS.append.md
```

Его содержимое необходимо добавить в существующий корневой:

```text
AGENTS.md
```

Важно: **не заменяйте существующий `AGENTS.md` целиком.**

Нужно именно добавить правила Web Platform Release Kit к уже существующим инструкциям проекта.

## Первый запуск Codex

После добавления Skill используйте запрос:

```text
$web-platform-release

Сначала только прочитай проект и проверь готовность MVP.
Ничего не меняй и не устанавливай без согласованного плана.

Не переписывай глобальные скрипты, архитектуру, баланс,
сохранения, зависимости и систему сборки.

Когда MVP готов, спроси, под какую платформу готовим первый SDK-билд.

После выбора платформы:
1. проверь актуальные правила площадки;
2. определи необходимый SDK;
3. предложи минимальную интеграцию;
4. перечисли файлы, которые потребуется изменить;
5. объясни назначение каждого изменения;
6. запроси разрешение перед изменением кода.
```

## Как Codex должен выбирать платформу

После анализа готового MVP Codex должен задать вопрос:

> **Под какую платформу готовим первый SDK-билд?**

Например:

```text
Яндекс Игры
CrazyGames
Poki
GameDistribution
Playgama
VK
Одноклассники / VK Mini Apps
```

Если платформа уже была явно указана ранее, повторно задавать тот же вопрос не нужно.

---

## Какие вопросы Codex должен уточнить

Перед интеграцией могут потребоваться уточнения:

- какая площадка выбрана;
- какой тип приложения создаётся;
- desktop, mobile или оба варианта;
- есть ли rewarded ads;
- нужны ли interstitial ads;
- нужны ли внутриигровые покупки;
- нужны ли облачные сохранения;
- нужен ли leaderboard;
- есть ли авторизация;
- какой SDK уже используется;
- есть ли готовый аккаунт разработчика;
- есть ли Platform ID / Game ID / App ID;
- какие функции уже подтверждены в кабинете разработчика.

Codex не должен спрашивать то, что уже известно из проекта или предыдущего диалога.

---

## Что Codex НЕ имеет права менять самостоятельно

Без отдельного разрешения запрещено глобально изменять:

- core gameplay;
- центральные GameManager / AppManager;
- экономику;
- баланс;
- систему прогрессии;
- систему сохранений;
- структуру сцен;
- глобальные события;
- архитектуру проекта;
- зависимости;
- package manager;
- версию Unity;
- версию Phaser;
- сборочный pipeline;
- настройки CI/CD;
- глобальный Input System;
- систему аналитики;
- формат существующих данных.

Также нельзя автоматически:

- делать `commit`;
- делать `push`;
- публиковать билд;
- принимать договор;
- подключать платный сервис;
- удалять рабочие системы;
- заменять существующий SDK другим;
- обновлять движок;
- мигрировать архитектуру.

## Правило минимального вмешательства

Каждая платформенная интеграция должна быть максимально изолированной.

Предпочтительная схема:

```text
Game Logic
    │
    └── PlatformService Interface
            │
            ├── YandexPlatform
            ├── CrazyGamesPlatform
            ├── PokiPlatform
            ├── PlaygamaPlatform
            ├── GameDistributionPlatform
            └── VKPlatform
```

Игровой код обращается к абстрактному сервису, а не напрямую к SDK портала.

Пример:

```text
showRewardedAd()
saveGame()
loadGame()
submitScore()
purchaseProduct()
getLanguage()
pauseGame()
resumeGame()
```

Конкретная реализация зависит от выбранной платформы.

---

## Отдельные сборки

Рекомендуется создавать отдельную сборку для каждой площадки.

Например:

```text
builds/
├── yandex/
├── crazygames/
├── poki/
├── gamedistribution/
├── playgama/
└── vk/
```

Не рекомендуется пытаться подключить все SDK одновременно в один production build без необходимости.

## Документы по платформе

После выбора площадки Codex должен создать или обновить отдельную папку документации.

Пример:

```text
docs/platforms/yandex/
```

В ней рекомендуется хранить:

```text
PLATFORM_PROFILE.md
INTEGRATION_PLAN.md
SDK_NOTES.md
PERMISSIONS_LOG.md
SOURCE_CHECK.md
TEST_REPORT.md
RELEASE_CHECKLIST.md
```

### PLATFORM_PROFILE.md

Фиксирует:

- название платформы;
- URL документации;
- используемый SDK;
- версию SDK;
- Game ID / App ID;
- формат сборки;
- поддерживаемые устройства;
- рекламу;
- покупки;
- сохранения;
- leaderboard;
- авторизацию;
- языки;
- ограничения.

### INTEGRATION_PLAN.md

Перед изменением кода Codex должен записать:

- какие файлы будут добавлены;
- какие файлы будут изменены;
- зачем они меняются;
- какие существующие системы затрагиваются;
- какие риски существуют;
- как откатить изменения;
- как проверить интеграцию.

После этого пользователь должен подтвердить изменения.

### PERMISSIONS_LOG.md

Используется для фиксации разрешений пользователя.

Пример:

```text
[APPROVED]
Добавить YandexPlatformService.ts

[APPROVED]
Добавить вызов pauseGame() перед показом рекламы

[NOT APPROVED]
Переписать существующую SaveSystem
```

Разрешение на одно изменение не распространяется автоматически на другие системы.

### SOURCE_CHECK.md

Перед подключением SDK Codex должен проверить актуальные официальные источники.

Необходимо зафиксировать:

```text
Дата проверки:
Платформа:
SDK:
Версия:
Источник:
Статус:
```

Важные функции должны иметь статус:

```text
CONFIRMED
NEEDS_VERIFICATION
NOT_SUPPORTED
```

Нельзя додумывать возможности SDK.

## Реклама

Рекламная система должна быть отделена от gameplay.

### Rewarded Ads

Награда выдаётся только после подтверждённого успешного завершения рекламы.

Нельзя считать наградой:

- открытие рекламного окна;
- закрытие окна;
- начало показа;
- ошибку SDK;
- timeout;
- повторный callback.

Нужно защищаться от двойной выдачи награды.

```text
Request Ad
    ↓
Ad Started
    ↓
Game Paused
    ↓
Ad Completed
    ↓
SDK confirmed reward
    ↓
Reward granted ONCE
```

### Interstitial Ads

Interstitial рекомендуется показывать только в естественных паузах:

- после завершения уровня;
- после завершения раунда;
- между сценами;
- после экрана результата.

Не рекомендуется показывать рекламу:

- во время активного управления;
- сразу после старта игры;
- после каждого действия;
- в момент критической игровой ситуации.

Частота должна настраиваться отдельно для каждой платформы.

---

## Сохранения

Система сохранений должна иметь общий формат данных.

Например:

```json
{
  "version": 1,
  "progress": {},
  "economy": {},
  "settings": {},
  "timestamp": 0
}
```

Платформенный слой отвечает только за место хранения.

Возможные варианты:

```text
LocalStorage
Cloud Save
Platform Storage
Account Storage
```

Нельзя переписывать существующий SaveSystem только ради подключения SDK.

---

## Leaderboards

Перед добавлением рейтинга необходимо проверить, предоставляет ли выбранная площадка настоящий leaderboard API.

Нельзя выдавать локально сгенерированную таблицу игроков за глобальный рейтинг.

Если API отсутствует:

```text
Global leaderboard = disabled
```

Можно оставить:

- личный рекорд;
- лучший результат;
- локальную статистику.

---

## Внутриигровые покупки

IAP подключаются только если:

1. платформа их поддерживает;
2. функция доступна конкретному аккаунту разработчика;
3. известны правила товаров;
4. обработана отмена платежа;
5. обработана ошибка;
6. предусмотрена защита от повторной выдачи;
7. проверено восстановление покупки, если это необходимо.

Для первого MVP покупки не являются обязательными.

---

## Пауза игры

При открытии рекламы, платёжного окна, platform overlay или системного диалога игра должна корректно приостанавливаться.

Минимально:

```text
pause gameplay
pause timers
pause audio
disable input
```

После закрытия:

```text
resume gameplay
resume timers
resume audio
enable input
```

---

## MVP сначала, SDK потом

SDK не должен использоваться как причина бесконечно откладывать завершение игры.

До платформенной интеграции желательно иметь:

- работающий core loop;
- начало и конец игровой сессии;
- управление;
- UI;
- сохранение;
- базовую прогрессию;
- стабильный restart;
- отсутствие критических ошибок;
- тестовую Web-сборку.

После этого начинается подготовка первой площадки.

---

## Рекомендуемая стратегия релиза

Не рекомендуется одновременно интегрировать 5–7 площадок.

Лучший порядок:

```text
1 игра
↓
1 законченный MVP
↓
1 платформа
↓
реальный релиз
↓
аналитика
↓
исправления
↓
2 платформа
↓
3 платформа
```

Так проще понять:

- работает ли сама игра;
- какие ошибки связаны с gameplay;
- какие ошибки связаны с SDK;
- как реагируют реальные игроки;
- насколько оправдан дальнейший порт.

## Возможный маршрут первого web-релиза

Для простых HTML5 / Phaser игр:

```text
Яндекс Игры
    ↓
CrazyGames / GameDistribution
    ↓
Playgama
    ↓
другие площадки
```

Для Poki обычно стоит готовить отдельную качественную версию и учитывать процесс отбора площадки.

Для VK и Одноклассников необходимо отдельно проверять актуальный маршрут публикации и используемые API.

## Поддерживаемые технологии

Kit рассчитан прежде всего на:

- HTML5;
- JavaScript;
- TypeScript;
- Phaser;
- Unity WebGL.

Также может использоваться с другими web-движками, если платформенная интеграция может быть вынесена в отдельный слой.

### Phaser / HTML5

Для новых небольших 2D web-игр Phaser / HTML5 часто позволяет:

- уменьшить размер билда;
- быстрее загружать игру;
- проще интегрировать JavaScript SDK;
- быстрее создавать отдельные платформенные адаптеры.

Но готовый Unity-проект не следует автоматически переписывать на Phaser.

### Unity WebGL

Для Unity WebGL необходимо отдельно контролировать:

- размер билда;
- время загрузки;
- память;
- compression;
- template;
- взаимодействие JavaScript ↔ Unity;
- fullscreen;
- focus;
- pause/resume;
- мобильные браузеры.

Платформенные API желательно подключать через изолированный bridge.

## Тестирование

Перед публикацией необходимо проверить минимум:

```text
[ ] Игра запускается
[ ] Нет ошибок в Console
[ ] Работает мышь
[ ] Работает touch
[ ] Работает restart
[ ] Сохраняется прогресс
[ ] Восстанавливается прогресс
[ ] Работает pause
[ ] Работает resume
[ ] Rewarded ad выдаёт награду один раз
[ ] Ошибка рекламы не выдаёт награду
[ ] Interstitial не ломает состояние игры
[ ] Звук корректно выключается при рекламе
[ ] SDK корректно инициализируется
[ ] Игра работает без SDK в dev-режиме
[ ] Нет секретных ключей в repository
[ ] Production build открывается напрямую
```

## Что уже проверено в Kit

В исходной версии утилиты прошли **22 теста**, включая:

- безопасное чтение проекта;
- анализ структуры Web-сборки;
- обнаружение потенциальных секретов;
- проверку существующих документов;
- защиту от случайной перезаписи файлов.

Это не означает, что любой SDK уже автоматически подключён к игре.

Каждая реальная интеграция всё равно требует:

- конкретного проекта;
- выбранной площадки;
- Game ID / App ID;
- тестового окружения;
- актуальной документации;
- браузерного тестирования.

## Безопасность репозитория

Нельзя хранить в Git:

```text
API secrets
private keys
service account credentials
passwords
payment credentials
private certificates
.env с секретами
```

При необходимости добавляйте локальные секреты в `.gitignore`.

---

## Основная философия проекта

Этот Kit не предназначен для автоматического переписывания игры под каждую площадку.

Его задача — сохранить стабильную игру и создать вокруг неё аккуратный платформенный слой.

> **Codex помогает интегрировать платформу в игру, а не переписывает игру ради платформы.**
